01 / Research
YOLO-Worldopen-vocabularyevaluation

Can a text prompt replace a trained detector?

Open-vocabulary detectors promise detection with no labelling and no training: type "person" and go. I measured what that shortcut actually costs, with the same backbone on both sides so the fight is fair.

  • The cost is uneven. Some classes gain nothing from training, others gain about 0.10 F1, so the answer depends on what you detect.
  • Two of my own hypotheses failed and the write-up says so: per-class thresholds did not hold up, and prevalence barely moved the best threshold.
  • mAP cannot choose a confidence threshold, because it already integrates the whole precision-recall curve. Precision, recall and F1 can.

02 / Production
DeepStreamTensorRTmulti-stream

Six detection systems on live camera networks

End to end for client camera networks: fire and smoke, drones, number plate recognition, pedestrian counting, face recognition and restricted-object detection. For each one I collected and annotated the data, trained the model and deployed it.

  • One GPU server ran several camera streams at once, so cost per camera, not accuracy alone, drove the design.
  • Night footage and small distant objects were the hard part. Plate recall only became usable once plates were tracked across frames instead of judged one frame at a time.
  • I work below the Python layer where it counts: a custom C++ detector output parser for DeepStream, with ONNX and TensorRT (fused NMS) so detections come out at frame rate instead of at demo rate. Threat detection and drone detection ran on that path, RTSP in and out.
  • For fire and smoke, a small custom CNN beat the obvious transfer-learning choices on the same data: 0.90 accuracy against 0.77 for ResNet50 and 0.78 for EfficientNetB0. Smaller, faster and more accurate at once, which matters when you pay for the GPU.
  • Models were retrained on the frames they actually failed on in production, not on more of the same easy footage.
  • Later automated the whole path from a new dataset to a TensorRT deployment artifact, with no manual steps.

Detecting pain in animals from video

A contactless health monitor that spots pain and anxiety owners miss, from video alone. The data was small, noisy and imbalanced, which is the normal state of real projects. I architected the system and led the build.

An EfficientNet vision model fused with behavioural anomaly scoring, shipped as an API on Azure. Suppliers send receipts in every format imaginable. I designed the architecture and led the build of an LLM system that extracts the right fields and structures them into bills of materials, whatever the layout.

Retrieval you can put a number on

Most retrieval systems ship on a feeling: someone tries five questions, the answers look fine, it goes live. I built and ran the benchmark that says whether the retrieval layer behind Qualzo is actually good, across 298,975 documents and five public BEIR datasets, with the results published on the product site.

  • Above the published baseline on all five datasets, same data and same metrics, so the comparison can be checked instead of taken on trust.
  • 100% valid structured output against 62% for the baseline approach. Malformed JSON is not a rounding error when a pipeline depends on it.

Normalising messy data with GPT for a US health company

Evolvv Health had raw records in spreadsheets with no fixed shape. I built the pipeline that sends them through GPT for analysis and normalisation and writes clean output back, run by the client whenever they need it.

  • Detects the column layout on every run and batches rows to fit the model's token limit, so any size of sheet goes through.
  • Retries rate-limited calls, logs skipped records without stopping the batch, and guarantees one output row for every input row.

06 / Platform
ClaudeTextractgeospatial

Decades of drilling reports, turned into maps

Exploration data arrives as scanned reports going back decades, every one laid out differently. I built the platform that pulls the tables out with AWS Textract, uses Claude to work out what each column actually is, and turns the result into interpolated grade maps a geologist can query.

  • Interpolation (Kriging and inverse distance weighting) is validated leave-one-out, so a convincing-looking map cannot hide a bad model.
  • Around 40 API endpoints behind it, from ingestion through to the map layer.

Approach

A model is only finished when it is fast, cheap and trusted.

01 · MEASURE

Your data, your number

An evaluation set built from your own cameras or documents, with metrics you can re-run after every change. Not a number copied from a model card or a leaderboard.

02 · ROBUST

Built for the hard cases

Night footage, blur and tiny objects for vision. Odd formats, ambiguous questions and missing fields for LLMs. The edge cases are where trust is won or lost.

03 · EFFICIENT

Cost per use, not per demo

Cost per camera, per document, per question. Optimised inference and the right-sized model, so the system scales without a bill that kills the project.

Questions

What people ask before we start.

Can you work with the cameras we already have?

Yes. If a camera puts out an RTSP stream, it can feed the pipeline, and several streams can share one GPU server. Nothing needs replacing, and the detection runs alongside whatever recording system is already in place.

How do we know it will work on our footage and not just in a demo?

Before anything gets built I put together an evaluation set from your own footage or documents and measure the current state of the art on it. You see the number first. If the number is not good enough, you find that out in week one rather than after the build.

Do you do LLM work as well as computer vision?

Both, and most projects end up needing both. Detection and video analytics on one side, agents, retrieval, document extraction and fine-tuning on the other. The common part is the engineering after the model works: latency, cost per unit, and output a downstream system can rely on.

What does a first engagement usually look like?

A short call to hear the problem and the number you need to hit, then a small scoped piece of work with a measurable outcome, usually an evaluation or a working prototype on your data. That keeps the risk low for you and tells us both quickly whether the full build is worth doing.

Where are you based and how does the time difference work?

Rawalpindi, Pakistan, UTC+5. That is a full working overlap with Europe and the Middle East, and mornings with the US. I work remotely with teams in all three.
